# Проект 1. Домашний стенд (VirtualBox)

Учебный стенд из двух виртуальных машин: изолированный внутренний сегмент, вход только по SSH-ключам, фаервол по принципу "запрещено всё, что не разрешено явно", управление целевым сервером через Ansible.

---

## 1. Цель

- Собрать две VM, связанные отдельным внутренним сегментом.
- Настроить доступ по SSH-ключам и полностью отключить вход по паролю.
- Защитить машины фаерволом с политикой default-deny.
- Научиться управлять целевым сервером через Ansible.

---

## 2. Архитектура

| Узел | Внутренняя сеть (192.168.1.0/24) | NAT-сеть (10.10.10.0/24) | Шлюз | Роль |
|------|----------------------------------|--------------------------|------|------|
| vm-deploy | 192.168.1.11 | 10.10.10.11 | 10.10.10.1 | управляющий узел |
| vm-app | 192.168.1.12 | 10.10.10.12 | 10.10.10.1 | целевой сервер |

**Назначение сетей:**

- **Внутренний сегмент `192.168.1.0/24`** — связь между виртуальными машинами. Маршрута по умолчанию в этой сети нет, наружу выхода тоже нет.
- **NAT-сеть `10.10.10.0/24`** — выход виртуальных машин в интернет и проброс портов с хостовой машины.

**Проброс SSH-портов (VirtualBox NAT Network):**

- `хост 127.0.0.4:2222 → vm-deploy:22`
- `хост 127.0.0.5:2222 → vm-app:22`

Оба проброса идут на один и тот же порт `2222`, но привязаны к разным loopback-адресам хоста (`127.0.0.4` и `127.0.0.5`). Это позволяет обращаться к разным машинам без изменения номера порта.

**Доступ с хостовой машины** организован через `~/.ssh/config` с алиасами `vm-deploy` и `vm-app` (параметры `IdentitiesOnly yes` и `StrictHostKeyChecking accept-new`).

---

## 3. Что сделано

1. **Виртуальные машины.** Две VM с Ubuntu 22.04, у каждой два сетевых адаптера: NAT и внутренняя сеть. Статические адреса настроены через netplan.
2. **SSH-ключи.** Сгенерированы две отдельные пары ключей: для доступа с хоста на обе VM и для доступа с vm-deploy на vm-app. Публичные ключи добавлены в `~/.ssh/authorized_keys`.
3. **Настройка SSH.** Основной файл `sshd_config` не изменялся. Все параметры заданы через drop-in файл `/etc/ssh/sshd_config.d/00-access.conf`.
4. **Фаервол.** Настроен nftables с политикой `drop` на цепочках input и forward. Разрешены только установленные соединения, интерфейс loopback, ICMP и SSH.
5. **Ansible.** Установлен на vm-deploy. Создан инвентарь с группой `app`. Проверка связи модулем `ping` проходит успешно (`pong`).

---

## 4. Безопасность

- Вход под root запрещён (`PermitRootLogin no`).
- Вход по паролю отключён (`PasswordAuthentication no`, `KbdInteractiveAuthentication no`).
- Доступ только по публичному ключу; для каждого канала используется своя пара ключей.
- Фаервол работает по принципу default-deny: всё, что не разрешено явно, отбрасывается.
- Цепочка forward закрыта, поэтому виртуальные машины не работают как маршрутизаторы.

---

## 5. Где споткнулся

**Проблема.** В файле `/etc/hosts` на vm-deploy адрес `vm-app` был указан как `192.168.1.11`, то есть совпадал с собственным адресом vm-deploy. Из-за этого команда `ping vm-app` отправляла пакеты "в себя" и показывала успешный результат, хотя до удалённой машины трафик не доходил.

**Было (неверно):**

```
192.168.1.11 vm-app
```

**Стало (верно):**

```
192.168.1.12 vm-app
```

**Как нашёл.** Сравнил адрес из вывода `ping` (`192.168.1.11`) с реальными адресами из команды `ip a`. Несовпадение и выдало ошибку.

**Вывод.** Любое утверждение о сети нужно подтверждать командой (`ip route`, `ip -br a`), а не полагаться на память.

**Контекст.** `/etc/hosts` — это локальный резолв имён, он нужен потому, что в стенде нет DNS-сервера. В реальной инфраструктуре резолв выполняет DNS, а `/etc/hosts` используется только для локальных статических записей.

## 6. Как проверить

**С хостовой машины:**

```bash
ssh vm-deploy          # вход по ключу, без пароля
ssh vm-app             # через проброс на 127.0.0.5
```

**На стенде:**

```bash
ip -br a               # адреса интерфейсов на обеих VM
ip route               # default via 10.10.10.1 — маршрут через NAT-адаптер
getent hosts vm-app    # должен вернуть 192.168.1.12
ping -c 3 vm-app       # с vm-deploy, должен обращаться к 192.168.1.12
sudo nft list ruleset  # политика drop, разрешены только SSH, ICMP, loopback
sudo sshd -T | grep -E 'passwordauthentication|permitrootlogin'
ansible app -i inventory.ini -m ping   # SUCCESS => "ping": "pong"
```

**Проверка сохранения настроек после перезагрузки** (выполнить на обеих VM):

```bash
sudo reboot
# после загрузки:
ip -br a
ansible app -i inventory.ini -m ping
```
